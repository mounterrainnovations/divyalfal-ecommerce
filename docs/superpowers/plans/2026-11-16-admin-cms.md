# Divyafal Admin Portal + CMS (Phase 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild `/dashboard` as a seven-section admin portal in the Atelier design system, and give it CMS control of the public site's images, copy, homepage curation, slideshow, settings and enquiries — on the existing Supabase project, with no new hosted service.

**Architecture:** Five additive Prisma models (`MediaAsset`, `ContentBlock`, `HomepageSection`, `Slide`, `SiteSetting`) plus `Enquiry`, each with a thin repository in `lib/repositories/`. `ContentBlock` carries a `draft`/`published` pair so editing never changes the live site until Publish, which calls `revalidateTag`. The admin UI becomes routed sections under `app/dashboard/`, replacing the single 1,220-line client component. The storefront's reads flip from Phase 1's `siteCopy` constants to published content **last**, so every earlier task is reversible.

**Tech Stack:** Next.js 16 (App Router, `middleware.ts`, `revalidateTag`), Prisma 6.18 + Supabase Postgres, Supabase storage, existing `jsonwebtoken` auth, existing TipTap editor, Vitest + React Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-16-divyafal-revamp-design.md`

**Depends on:** `docs/superpowers/plans/2026-11-16-storefront-revamp.md` — Phase 1 must be complete. Task 4 of that plan defines the `page.section.field` keys this plan's seed writes.

## Global Constraints

- **`Product` is never altered, and never written by the seed.** Additive DDL only; no destructive statement in any migration file. Spec §5a.2.
- **Migrations and the seed run against the production Supabase database,** owner-authorised, under these guardrails, none of which may be skipped for speed: snapshot the project first; apply to a scratch schema and confirm additivity before production; `prisma migrate deploy` stays a deliberate manual action and is **never** added to the build command; the seed is idempotent (upsert by `key`) so a re-run cannot duplicate or clobber.
- **No new hosted service, no new paid dependency, no email delivery.** Enquiries persist to the DB and are read in the portal.
- **Auth:** the existing JWT and `/api/admin/login` stay. Enforcement moves into `middleware.ts` for `/dashboard` and `/api/admin/*`. `/api/upload` gains the server-side admin check it currently lacks.
- **`/api/slideshow` keeps its exact response shape `{ images: string[] }`.** `/api/products` and `/api/homepage-sections` keep their contracts.
- **Design:** the Phase 1 Atelier tokens and both families, tightened for density — small type, compact rows. No pills, no gradients, no `rounded-3xl`.
- **Media:** `MediaAsset` owns every asset including existing product photos, backfilled by matching the stored URL string (no `Product` FK). Deletion is blocked while an asset is referenced by `Product.photos`, `ContentBlock.draft`/`published` JSON, or `Slide`.
- **Placeholder garment fallbacks stay** as the empty-curation fallback. Spec §5a.1.
- **`public/collection`, `public/mostrec` and `public/shop by style` are not migrated** into Supabase storage. Spec §5a.1.
- **Verification gate per task:** `npm run lint` and `npm test` pass. Final gate: `npm run build` plus the Phase 1 Lighthouse targets re-run on `/`, `/products`, `/product/[id]`.
- **Branch:** `feat/atelier-revamp`. No pushes to `main`.

## Review Focus

1. **The seed run twice** — the cutover runbook may re-run it, and a non-idempotent seed would duplicate blocks or overwrite content the client has since edited. Re-running must be a no-op on `published` values that already differ from the seed. → Task 2.
2. **Deleting a media asset still in use** — the client's most destructive available action, and the one with no FK to protect it. Deleting an asset whose URL appears in `Product.photos` must be refused with a usable message, and must not remove the storage object. → Task 6.
3. **An unauthenticated request to `/api/admin/*` or `/api/upload`** — upload today has no server-side auth at all, so anyone can write to the client's storage bucket. Every admin route must answer 401 without touching the DB or storage. → Task 3.
4. **A contact form submission that is empty, oversized, or repeated 100 times** — the endpoint is public. Missing required fields must 400, an oversized body must be rejected before it reaches the DB, and repeat submissions from one IP must be rate-limited. → Task 10.
5. **A publish whose `revalidateTag` fails, or a block whose `published` is still null** — the storefront must render the Phase 1 fallback copy rather than an empty page or a 500, and the publish must report partial success honestly. → Tasks 4 and 17.
